Worked Example

What goes in a skills.md file.

A strong skills file packages a repeatable workflow, not a vague aspiration. The example below shows the parts that matter: purpose, inputs, process, and output contract.

Open parent concept Open quickstart Open decision guide

Example skills.md

---
name: API Review
description: Review an API change for naming, versioning, consistency, and breaking changes.
inputs:
  - OpenAPI spec or endpoint diff
  - Current API standards
outputs:
  - Findings list ordered by severity
  - Recommended contract changes
  - Release risk summary
---

## Purpose
Review an API proposal or diff and produce a concise, actionable review.

## Steps
1. Identify the changed endpoints, schemas, and error contracts.
2. Check naming and resource consistency.
3. Check versioning and backward compatibility.
4. Flag breaking changes and suggest mitigations.
5. Summarize findings in severity order.

## Output Format
- Critical findings
- Medium findings
- Low findings
- Suggested revisions
- Ship / do-not-ship recommendation

Why this works

Specific purpose

The skill owns one job. It does not try to review architecture, product scope, and security policy all at once.

Clear inputs

Anyone invoking the skill can tell what artifacts are required before the workflow starts.

Stable output contract

The findings are returned in the same structure every time, which makes review and downstream automation easier.

Reusable steps

The workflow is generic enough to reuse across many API changes without rewriting the skill every week.
