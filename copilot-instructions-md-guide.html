Making the copilot-instructions.md file.

A good copilot-instructions.md file is short, durable, and specific. It should encode team-wide rules that need to hold across many prompts, not one-off task details.

Open parent concept Read quickstart Use decision guide

How to write it

Start with persistent rules only.

Add standards that should shape nearly every coding session: naming, testing, validation, documentation, and repo-specific expectations.

Keep the file scoped and readable.

Prefer a few clear sections over a long wall of policy. If a rule is hard to follow or easy to forget, rewrite it more concretely.

Write rules as actions.

Use direct statements such as “validate touched files” or “prefer focused edits.” Avoid abstract slogans that do not change behavior.

Separate permanent guidance from workflows.

If the content describes a reusable task sequence, it probably belongs in a skill. Instructions should shape behavior, not become a mini-runbook library.

Rule of thumb: if the assistant should follow it even when the user forgets to mention it, put it in copilot-instructions.md.

Starter example

# copilot-instructions.md

## Editing Rules
- Prefer small, focused changes.
- Preserve existing style unless the task requires a change.
- Avoid touching unrelated files.

## Validation
- Run the narrowest useful validation after edits.
- If validation cannot be run, explain why.

## Documentation
- Update docs when behavior or setup changes.
- Keep examples copy-ready.

## Collaboration
- Ask only when a missing choice blocks progress.
- Otherwise, take the next useful action.
Good content

Standards, validation expectations, editing boundaries, and collaboration rules.

Bad content

Temporary sprint context, one feature spec, or a long task checklist that only applies once.
